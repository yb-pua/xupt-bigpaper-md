## 1. 当前论文真正的核心故事

### 1.1 一句话主轴（已确认，评审认为成立）

> **"一个人的身份，经过一次认证，管住一台设备、放行一类服务、贯通一条审计链。"**

信任递进：
- 方向一（第3章）＝**凭证是谁的**——生物特征→稳定密钥→生物 DID→KGC-TEE 派生 SM9 私钥→AS-REQ 前置验签（用户认证入口）；
- 方向二（第4章）＝**凭证从哪来**——设备 DID→KDC 签发授权+ST(NetPerm)→中继代理签名+三重验证→SM9 密钥协商隧道（设备入网通道）；
- 方向三（第5章）＝**凭证能干什么**——双 DID（用户生物+Agent 设备）→双 ST（ST_net/ST_data）→双 SM9 签名链→MCP 四步验证（服务/工具授权）。

抽象主线：**可信身份 → 可信设备 → 可信网络 → 可信服务/Agent 协同 → 可审计授权链**。三个方向不是并列关系，而是"人→设备→Agent/服务"、"身份→网络准入→资源/Tool 授权"、"认证→授权→执行"的逐层扩展。

### 1.2 故事是否足以支撑完整学位论文——判断

**成立，但叙事必须在 3 处缝合"方向之间的衔接"，否则会被读成三个独立系统**：

1. **方向一 → 方向二**：人的凭证如何变成设备的凭证？——已有机制：绑定表 `user_bio_did ↔ device_did`（B1 联动校验："先认证用户，再授权设备"）。叙事上要在第4章 4.1 写"设备入网以前置的用户认证为前提"。
2. **方向二 → 方向三**：设备凭证如何变成服务/工具授权？——已有机制：ST_net（组网）与 ST_data（数据/协同）分级签发，中继验证 ST_net、MCP 服务端验证 ST_data。叙事上要在第5章 5.1 写"Agent=特殊设备节点，复用第4章组网准入，叠加第3章用户责任主体"。
3. **方向一 → 方向三**：用户责任主体如何贯穿到 Agent 指令？——已有机制：签名链 `σ_user=Sign(生物私钥, H(Cmd‖σ_agent‖ctx))`。叙事上这是"责任主体"与"执行主体"的解耦，是第5章区别于纯 OAuth 的核心。

**结论**：主轴成立；每章"承接上一章"的语句已定（方向设计汇总版 §2 末段），只需把上述 3 个缝合点写进各章 问题链 小节。

## 2. 三个方向如何统一（统一对象判定）

### 2.1 统一语义对象判定表

| 对象 | 方向一 | 方向二 | 方向三 | 是否统一 | 判定 |
|---|---|---|---|---|---|
| **ST 票据** | 签发标准 TGT/ST（ticket_id 字段） | ST 扩展 NetPerm（组网权限） | 双 ST：ST_net + ST_data（claims={tools,actions}） | ✅ | **跨三方向统一授权载体**，结构一致（字段扩展），应提升为统一安全语义 |
| **DID** | 生物 DID（`didsm9:<user_id>:<SM3>`） | 设备 DID（`make_device_did`） | 用户生物 DID + Agent 设备 DID | ✅ | **跨主体统一身份抽象**，同一 `did.py` 方法 |
| **ticket_id** | KDC 签发生成 | 中继验证日志关联 | MCP 调用→审计记录关联 | ✅ | **跨网络和应用统一审计关联键**，同一 `audit_logger` |
| **SM9** | 签名/验签/私钥派生 | 授权+代理签名+密钥协商 | 双签名链验证 | ✅ | 全链路国密支撑 |
| **Policy/Claims** | — | NetPerm{服务,带宽,时段} | claims={tools,actions} | ✅ | 统一为"权限声明"，同一 `claims_checker` 校验入口 |
| **KDC（TEE）** | KGC-TEE 派生 | 授权+代理委托 | 双 ST 签发 | ✅ | 同一 `kdc_tee.py` |
| **Warrant/代理授权** | — | 中继代理签名（warrant 限定） | 复用 relay 思路 | ⚠️ 方向二特有 | 方向二创新点，非三方向共通语义 |
| **签名链** | 预留 `verify_chain` | — | 双签名链（σ_agent→σ_user） | ✅ | 方向一预留接口→方向三实现 |
| **Audit** | 派生审计 | 准入/转发审计 | 调用审计 | ✅ | 同一 `audit_logger.log(ts, ticket_id, action, result, principal)` |

### 2.2 三个统一语义（提升为叙事主线）

1. **ST（含双 ST）= 统一授权载体**：身份认证的产物是一张 ST；网络准入的凭证是 ST(NetPerm)；MCP 服务授权是 ST_net+ST_data。全文"授权"只有一个对象。
2. **DID = 统一身份抽象**：人、设备、Agent 三类主体共用同一 `didsm9` 身份空间，SM9 以 DID 为标识公钥，"身份即公钥"贯穿三章。
3. **ticket_id = 统一审计关联键**：KDC 签发→中继验证→MCP 调用→审计记录，全链可回溯。第 6 章用一次端到端调用把 ticket_id 链条走完。

**评审要求**：论文正文把这 3 个对象从"工程变量"提升为"统一安全语义"，在绪论（第1章 1.3）与相关技术（第2章）各写一段"统一语义"说明，第 6 章综合展示。这是答辩时回答"三个系统拼接"质疑的根。

## 17. 答辩专家最可能问的 10 个问题及回答逻辑

1. **"生物特征熵有限，凭什么当身份根？"** → 答：身份根不是生物特征本身，而是"生物密钥驱动的 SM9 私钥"；模糊提取+多数投票把含噪熵源转化为可再生的密钥材料，密钥再经 SM9 派生体系进入密码域；A1 实测 KRR=0.986、FAR=0(5000对)、EER=0.027 支撑可行性；隐私侧用非存储式 σ+key_hash 兜底。
2. **"为什么不直接 PKINIT/证书？为什么用 SM9？"** → 答：免证书（标识即公钥，DID 即公钥）、国密标准化（GMT 0044/GB 38635）、密钥尺寸小；A4 以 128bit 安全级归一给出理论复杂度矩阵（SM9 验签约为 SM2 的 2-4 倍、RSA-2048 的 10²-10³ 倍，换取免证书与国密合规，属可接受权衡）。
3. **"SM9 验签 409ms 是不是太慢？"** → 答：A4 是 gmalg 纯 Python 原语级测量（非 AS-REQ 流程级），且仅 SM9 vs SM2 同实现可比；AS-REQ 流程级、RSA/ECDSA 跨实现对比已从论文删除，换成理论复杂度矩阵，避免"Python vs C 苹果比橘子"。
4. **"cross KRR=0.313 / 遮挡 0.167 这么低，方案是不是不行？"** → 答：这两项是"单张对单张"口径，不是方案使用方式（登记侧投票后 BER ~15 落 RS t=32 容限内）；遮挡弱是真实结果，由 L2 熔断兜底，与 A5-5 交叉印证；论文如实呈现并解释口径。
5. **"中继不能解密，凭什么还能做准入和转发？"** → 答：中继=验证型网关：验证 SM9 授权+ST+DID 一致性后按明文虚拟地址头路由，不解密载荷（SM4 密文+SM3 完整性）；"能不能准入"取决于票据验证，不取决于解密能力；B4-4 恶意中继实测明文泄露率=0。
6. **"代理签名会不会变成新的攻击面？"** → 答：warrant（授权书）限定中继只能签发"通过三重验证设备的会话准入凭证"，不能签新授权/新票据；伪造边界=授权书范围，D2 伪造测试 forge_ok=0；中继无 KDC 主密钥。
7. **"为什么不用 OAuth 2.1 直接解决 MCP 安全？"** → 答：OAuth 授权态缓存复用→调用者混淆可打穿（C3-6 已忠实复刻实测），server 级权限粒度粗、撤销慢；本文每请求携带双 ST+双签名链认证器，工具/动作级权限匹配；MCPS/SMCP 佐证同阶段密码化共识，本文定位互补。
8. **"三个方向是不是三个系统拼接？"** → 答：统一语义（ST=DID=ticket_id）贯穿：认证产 ST→准入验 ST→服务用 ST；DID 统一三类主体；ticket_id 全链审计；共享底座（sm9_engine/did/kdc_tee/audit_logger）复用，第6章端到端联动场景（用户→设备→Agent→MCP 一次调用）实证整链。
9. **"实验里有多少是模拟/自环/硬编码？"** → 答：如实清单——SM9 用 gmalg（部分模拟项标注"SM9 模拟"）、TEE 用独立进程模拟、NAT 用虚拟层模拟、MCP 用 JSON-RPC 模拟（标注"MCP 模拟"）、无 LLM/SDK；方向二/三已列修复清单，修复后所有数值可复现（固定 seed+README 元数据）。
