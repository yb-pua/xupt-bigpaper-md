# 三方向设计与论文组织（事实源）

> 单一事实源（2026-08-17 重构）：三方向链路、共享底座、数据流转、MCP 兼容、论文组织。

## 1. 三方向链路与共享底座

```
方向一（用户身份层）          方向二（设备组网层）          方向三（应用权限层）
生物特征→bio_key→生物DID ──→  设备标识→设备DID ──────────→  双DID: 用户生物DID + Agent设备DID
KGC-TEE 派生 SM9 私钥          KDC 签发 ST(NetPerm)          KDC 签发数据/协同权限 ST
AS-REQ 验签认证 ──────────→    中继代理签名+三重验证 ──────→  MCP 验证 签名链 + 双 ST
（用户认证入口）               （组网准入）                  （协同权限管控）
```

共享底座（方向一实现、二/三复用）：did.py（生物+设备 DID）/ sm9_engine.py（签名、验签、密钥协商、私钥派生、verify_chain、proxy_*）/ kdc_tee.py（KDC 单实例）/ ticket.py（ST 签发验证，claims 扩展）/ binding_table.py（用户↔设备绑定）/ audit_logger.py（ticket_id 审计链）。

## 2. 对比试验全景（11 组）

- **方向一（4 组）**：生物密钥 vs 口令（拦截率表）/ 模糊提取 vs 文献（参考表）/ SM9 vs PKINIT（性能图+定性矩阵）/ Kerberos 增强 vs 标准（流程对比图）——详见《方向一设计-C1C6.md》。
- **方向二（4 组）**：ST 授权 vs 传统 VPN（授权粒度/撤销时延）/ 代理签名 vs 直接持钥（伪造能力测试）/ SM9 密钥协商 vs IPsec/TLS（握手/吞吐/中继不可解密）/ P2PVPN vs 中心化（单点故障/规模）。
- **方向三（3 组）**：双 DID 分级授权 vs MCP 现状（权限模型对比表）/ 签名链+双 ST vs 单签名（篡改拦截率+时延）/ 端到端 vs 无管控（接入控制/审计）。

## 3. 票据存储与数据流转证明

- **存储**：TGT/ST 客户端缓存（ccache），KDC 无状态；撤销靠短 TTL（30min）+熔断+重签。
- **流转证明**：ticket_id 关联链——KDC 签发生成 ticket_id → 中继验证日志 → MCP 调用携带 → 审计记录（ts, ticket_id, 双DID, tool, 判定）。方案：A ticket_id 关联链（推荐）/ B 集中审计日志 / C 中继三重验证记录。

## 4. MCP 兼容（不改 MCP 协议）

| 方案 | 做法 | 兼容性 | 改动量 |
|---|---|---|---|
| A 网关层接入 | 中继做 MCP 网关，认证在网关层 | 零改动 | 中 |
| **B 头部注入（推荐）** | 请求附 ST（header `X-ST-Ticket`） | 报文不变 | 小 |
| C 服务端中间件 | 服务端前加验证中间件（验 ST+签名链） | 部署加层 | 小 |
| D OAuth 映射 | 认证映射 MCP OAuth（ST 等价 token） | 完全生态 | 大 |

推荐 B+C。调用链：Agent 指令（双 DID 签名）+ 双 ST（header）→ 中继验证 → MCP 中间件验 ST+签名链 → 权限匹配（claims_checker）→ 转发 → 审计（ticket_id）。
