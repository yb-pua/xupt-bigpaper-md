### 缺口→本文补充（非"别人没做过"）

1. **生物身份×标识密码×票据认证三重正交集成**：各自领域均有单点工作（生物密钥、SM9 签名、Kerberos 票据），但未见把"生物密钥做身份源→SM9 派生密钥→重构 AS-REQ"串成一条链的完整方案（本文创新点 1）。
2. **ST 作为统一授权载体贯通三层**：Kerberos 票据只管服务，OAuth token 不管网络准入，本文用 ST 同时承载准入、通信、数据调用授权——这是缺口，不是罗列。
3. **双主体（用户+设备）与 Agent 双签名调用级授权**：OAuth 无调用者绑定、Agent 委托无用户绑定，本文"Human DID+Agent DID+双 ST+双签名"补调用级可归因（创新点 3）。
4. **MCP 无认证现状有实证**（Zhou 等 40.55% 无认证）：本文提供"无认证/OAuth/本文"三方案同环境对比，把 MCP 安全问题从"论文断言"变成"可复现对照"。

### 使用红线

- 对比矩阵仅用于定位缺口，**不宣称全面优于**；性能/审计等每格必须给判定依据（协议规范引用或本文 CSV）。
- OAuth/MCP 侧负面结论基于本文复刻实验（`expC3_attack_matrix.csv`），须标注"自实现复刻（cache_auth_state=True）"，非对真实 OAuth 服务的声明。

格式：创新点 → 已有研究缺口 → 本文新增机制 → 代码实现 → 实验 → 对比基线 → 安全属性 → 最终结论。创新点 1=核心，2=递进，3=应用验证，三个不同级。

### 创新点 1（核心创新）：生物特征模糊提取 + SM9 + Kerberos → "可信身份建立"

- 已有研究缺口：生物认证存储模板易泄漏、口令可被爆破、Kerberos 口令认证无法防票据伪造；三者各自有工作但无集成。
- 本文新增机制：非存储式模板（σ=码字⊕W_ext，随机盐每次 Gen）→ SM9 生物密钥派生 → AS-REQ 前置 SM9 验签替代口令。
- 代码实现：`core/fuzzy_extractor.py`、`core/secure_template.py`、`core/registration.py`、`core/kerberos_enhanced.py`（exp1 core 13 模块）。
- 实验：A1 密钥恢复（vote5 KRR=0.986，single=0.287，FAR=0/5000对，EER=0.0265，AUC=0.9889）；A2 噪声（亮度 0.99/遮挡 0.167）；A3 端到端 96.7%+熔断；A5 9/9 攻击拦截+σ 熵 7.08B+W 熵 74.36bit。
- 对比基线：single（无投票）0.287 vs vote5 0.986；SM9 vs SM2/RSA 原语时延；模板逆向文献（TIFS2021）。
- 安全属性：不可存储泄漏、不可链接、不可伪造、可审计、退化解耦（L2 兜底）。
- 最终结论：在投票生效条件（多帧同源）下，生物密钥可高可靠恢复并替代口令完成 Kerberos 初始认证；在单帧/遮挡条件下如实退化，由投票与熔断兜底。**结论只写"有效工况+退化工况"，不夸大。**

### 创新点 2（递进机制）：ST + DID + warrant + P2P → "可信设备准入和安全通信"

- 已有研究缺口：Kerberos 票据只管服务访问不管网络准入；WireGuard 管组网不管身份授权；ZTNA 有准入但少与国密票据/审计贯通。
- 本文新增机制：ST 票据同时承载准入+通信授权，warrant 限定授权范围，DID 绑定设备，数据面 SM4 隧道。
- 代码实现：exp2 `expB0_discovery_nat.py`、`expB1_access.py`、`expB2_scalability.py`、`expB4_attacks.py`。
- 实验：B1 7 类攻击全拦+legal 放行；B4 601/601 拦截（含恶意中继）；B2 扩展性（回环趋势）；NAT 分类真值。
- 对比基线：OpenVPN 控制面握手（p50=110ms）；无准入对比组。
- 安全属性：ST 合法、DID 绑定、warrant 受限、抗重放/伪造/篡改/冒用、端到端加密。
- 最终结论：ST 准入机制可拦截准入与通信类攻击；数据面与性能为回环模拟，只作趋势性结论。**必须如实标注模拟，只写已测。**

### 创新点 3（应用验证）：Human DID + Agent DID + 双 ST + 双签名 → "应用层协同授权能力"

- 已有研究缺口：MCP/Agent 调用普遍无认证或弱认证（40.55% 无认证实证）；OAuth 授权态缓存无调用者绑定；Agent 委托无用户绑定。
- 本文新增机制：环境标识→设备 DID；用户生物 DID+设备 DID 绑定；双 ST（ST_net 组网+ST_data 数据）双签名链；四步验证（双 ST→双签名→DID==Principal→ClaimsChecker tool+action）。
- 代码实现：exp3 `expC0_agent_id.py`、`expC1_scenarios.py`、`expC3_attacks.py`、`expC4_security_matrix.py`。
- 实验：C0 200 DID 零冲突+克隆检测；C1 3 场景 passed+审计链 1.0；C3 六类攻击 100% 拦截 vs OAuth/noauth 0%；C4 7 维矩阵。
- 对比基线：无认证、OAuth 2.1（自实现复刻 cache_auth_state=True）。
- 安全属性：用户-Agent 绑定、调用级绑定、tool+action 级授权、抗重放/篡改/越权/冒用/混淆、审计归因。
- 最终结论：在 MCP 应用验证场景下，双主体授权链可提供 OAuth/无认证不具备的调用级安全属性。**定位=应用验证，不宣称全面优于 OAuth；性能（C2）重测前不作任何结论。**

## H. 《端到端实验设计》

目标：证明"三方向不是三个孤立模块，而是一条完整安全链"。**不新增架构，只组合现有模块。** 由 Human→Biometric→Bio-DID→KDC→ST→Device-DID→P2P准入→Agent-DID→Agent ST→User ST→Dual Signature→MCP→Tool→Audit(ticket_id) 串链。

### 组合来源（全部现有代码）

| 链环节点 | 复用模块 | 所在代码 |
|---|---|---|
| Human→Biometric→Bio-DID | 人脸采集+稳定位+模糊提取+登记 | exp1 `core/face_embedder.py`/`fuzzy_extractor.py`/`registration.py` |
| →KDC→ST | AS-REQ 前置验签+发 ST | exp1 `core/kerberos_enhanced.py`/`kdc_tee.py` |
| →Device-DID→P2P准入 | 设备 DID+ST 准入校验 | exp2 `expB1_access.py`/`core` |
| →Agent-DID→Agent ST→User ST→双签名 | 双 DID+双 ST+双签名链 | exp3 `core`/`expC1_scenarios.py` |
| →MCP→Tool | MCP JSON-RPC tools/call + ClaimsChecker | exp3 `core` |
| →Audit(ticket_id) | 审计链贯通 | exp3 `expC1_audit.py`（ticket_id 贯通率） |

### 被测指标

| 指标 | 定义 | 期望/验收 | 断言来源 |
|---|---|---|---|
| 总时延 | 链首→链尾（含全部验签） | 记录 p50/p90/p95 | 时间戳采集 |
| 各阶段时延 | 每环节分段时延 | 记录 | 时间戳采集 |
| 成功率 | 合法请求全链通过比例 | ≥ 链路组件正常率的乘积，如实 | 逐链测试 |
| 攻击拦截 | 链上任一点插入攻击（伪造 ST/篡改指令/重放） | 100% 拦截 | 复用 B4/C3 攻击样例 |
| 授权链完整率 | 每请求 ST/签名链/DID 绑定校验全过 | 100% | 复用 C1 口径 |
| 审计链完整率 | 全链 ticket_id 贯通 | 通过路径 100% | 复用 `expC1_audit.csv` 口径（拒绝类无票，如实） |

### 实施要点

1. 单脚本 `expE2E_pipeline.py`（新文件，不重构）编排现有模块，串行跑 N=30 合法请求 + 3 类攻击注入。
2. 每次请求记录分段时延与最终 ticket_id，输出 `results/expE2E_summary.csv`（含 meta seed/口径）。
3. 安全与性能口径沿用既有规则：纯 Python/GIL/回环模拟全局声明一次；攻击复用 `expB4_attacks.py` 与 `expC3_attacks.py` 的用例；审计缺失口径=拒绝路径无票。
4. 产出 F8 图与 T15 表的数据源。

### 验收红线

- 本实验完成前，论文 §7 只写"架构上贯通"的设计论证；**实证结论（时延/成功率/拦截）必须在 E2E CSV 存在后写入。**
