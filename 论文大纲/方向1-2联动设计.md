# 方向1 ↔ 方向2 联动设计与数据规划

> 回答两个问题：①方向1（生物认证）与方向2（ST票据P2PVPN）如何联动；②联动需要什么数据。
> 配套：`实验需求点清单.md`、`方向二实验设计详解.md`。

## 1. 联动本质：Kerberos 框架内的"认证→授权"链路

方向1重构的是 **AS**（用户初始认证），方向2的 KDC 即 **TGS** 角色（为设备签发组网 ST）。两者在标准 Kerberos 流程中是同一链路的两环：

```
[方向1：谁是你]                        [方向2：你能干什么]
用户生物认证(AS-REQ: SM9签名)
   └─ 签发 TGT ──用TGT向TGS──┐
   ┌──────────────────────────┘
   ├─ KDC(TGS) 校验 TGT → 签发绑定设备DID的组网ST(NetPerm)
   ├─ 设备携带 ST+授权 → 中继三重验证(授权/票据/DID一致性+绑定校验)
   └─ SM9密钥协商 → 安全隧道 → 端到端通信
```

**意义**：方向1的认证结果为方向2的授权提供主体身份依据——"先认证用户，再授权设备"，符合零信任"人-设备绑定、持续验证"逻辑；同时也让方向1的 TGT 体系直接复用，不引入第二套信任根。

## 2. 三层联动机制

| 层 | 联动内容 | 实现要点 |
|---|---|---|
| 身份层 | 方向1产出用户生物DID（did:bio）→ KDC 登记**绑定表**（user_bio_did ↔ device_did） | 绑定表为 KDC 内部数据，随 ST 签发时校验 |
| 协议层 | ①用户先 AS-REQ 获 TGT；②用 TGT 换设备组网 ST（TGS-REQ 携带 TGT+设备DID+NetPerm 申请）；③设备入网时中继附加"绑定校验"（设备请求须关联已认证用户） | B1 准入新增用例：无绑定/绑定用户未认证 → 拒绝 |
| 数据层 | 方向1注册产物（生物DID、R_digest）作为绑定表输入 | 生物DID 是密码学产物，模拟生成即可，不需真实人脸 |

## 3. 联动数据规划

| 数据 | 来源 | 用途 | 关联 |
|---|---|---|---|
| LFW 人脸 + InsightFace 特征 | 公开（已有 824MB 数据集） | 方向1：密钥恢复/投票实验 | 产出用户生物DID |
| 用户-设备绑定表 | 程序生成（N_user × M_device，含绑定/未绑定两类） | 方向2 绑定校验用例 | 输入为生物DID 摘要（模拟） |
| 设备 DID 样本 | 程序生成（N=10~200） | 方向2 组网/扩展性 | 与绑定表关联 |
| 业务流样本 | 程序生成（三型） | 方向2 整形实验 | — |
| 集成实验数据 | 方向1认证 → 换ST → 入网 → 通信全链路 | 跨方向验证（P2） | 复现"认证-授权"闭环 |

**注意**：方向2 本身不需要真实生物数据；绑定表用模拟生物DID 即可，但集成实验中"用户认证→设备入网"应跑真实方向1代码（真实 LFW 特征）打通链路。
